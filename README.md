# Copilot Skills, Agents & Reference Packages

Reusable GitHub Copilot skills and agents for structured thinking, writing, and analysis, plus a set of reference packages on observability and engineering practice.

## Skills (`skills/`)

| Skill | What it does |
|-------|-------------|
| **arc42** | Turn raw, unstructured source material about a system into arc42-structured architecture documentation — twelve chapters, ISO/IEC/IEEE 42010 ordering (stakeholders, concerns, then views). Populates what the sources support and states the gaps plainly rather than filling them. Ships with a complete worked example. |
| **artifact-review** | Evaluate artifacts from expert perspectives using selectable review lenses (usability, clarity, stakeholder fit). |
| **briefing** | Produce stakeholder briefing products using intelligence, military, and business communication standards (BLUF, SOF, options lists). |
| **capability-views** | Early release (0.1). Describe one business capability in a register of CSV tables, from the code, documents and people you point it at, and draw its design-for-operations views as one self-contained HTML page: the map (capability, flows, stages, steps, the parts carrying each step and what they depend on), what each layer could report, each AI agent as a system of its own, and where a failure reaches. Every row cites where it came from and is marked extracted, proposed, gapped or ratified; a blank cell is drawn as not assessed, never as absent. Design time only. Uses the design-for-operations skill's code reader when it is installed. Ships the blank register and its column definitions, the method's closed lists, the drawing program (Python 3, standard library only) with its tests, and a filled register for a public sample shop. |
| **confluence-design** | Design or review a Confluence page for reader-task-fit — top-task prioritization, macro-as-format selection, page composition, answer-first ordering. |
| **dashboard-evaluation** | Evaluate a dashboard that already exists — panel by panel, with a stated reason per panel — or design a new one before any layout. Asks whether the surface answers the questions its reader actually has, whether each panel is drawn in the right form for its question, and whether the page can be read at all. Produces a keep / fix / remove record the owner can dispute line by line. |
| **design-for-operations** | Work out what a business process flow actually does, which code implements each part of it, and what could be watched — from source, with a file and line under every mechanical claim. Runs as a nine-phase skill over a bundled Semgrep-based extractor, or fits your own code-analysis tool and scores the fit with exit codes. Includes a worked example on a public reference application. |
| **doc-check** | Evaluate documentation against the Diataxis 4-type framework (tutorial, how-to, reference, explanation). |
| **editorial** | Editorial governance for human-facing content — tone/style, production standards, writing craft. |
| **grafana-dashboards** | Create, clone, modify, re-lay-out or bulk-change Grafana dashboards (Grafana 13, classic and v2 JSON) without regressions. Each change is declared before it is made and made by editing the dashboard Grafana returned; two bundled scripts fail on any change nobody declared, any declared change not made and any panel whose numbers move unexpectedly, save with a conflict check, and re-check that earlier fixes still hold. A short design brief per dashboard keeps it coherent as it grows. Ships a first-run probe that tests the Grafana behaviours it relies on, the list of those behaviours with their sources, a maintainer guide, a template for local conventions, and its tests. |
| **html** | Produce interactive, self-contained HTML shaped for a specific job (understand, brief, present, orient, reference). Includes 20 worked examples. |
| **model-lookup** | Surface the conceptual models already built for a domain — the typed-slot structures (chains, stacks, sets, graphs) catalogued in a companion compendium — that fit the work in front of you, on the cue "what are the models for this?". Names the fit (one model, a composition, or none) instead of reinventing. Ships with the compendium it reads. |
| **prior-art-check** | Check whether something you built already exists as established practice — a named practice, a standard artifact, or a framework — or is genuinely novel. Judges by function rather than by name, and reconciles what it finds against your own record of adopted practice. Ships with the definition it judges against. |
| **prune-instructions** | Restructure an overgrown instructions file via the residency-test method (GATE / FACT / CONDUCT). |
| **requirements** | Elicit and structure requirements before work begins — functional requirements, quality attributes, stakeholder analysis, failure definition. |
| **right-thing-right-way** | Two-altitude diagnostic: am I solving the right problem? am I solving it the right way? |
| **room** | Put several advisors on one problem at once — an engineer, a mentor, a domain practitioner, a cold reader of the record — each in its own context, each blind to the others, each reporting separately. Implements Perspective-Based Reading, where the gain is the union of what the perspectives find and collapses when they overlap, so seats are chosen by question shape rather than by headcount. Ships 19 seat prompts, a convening procedure with three mechanical controls against a room grading its own work, and a scoring ledger that states its own falsifier. |
| **skill-creator** | Create, modify, and evaluate Copilot skills. |
| **systems-analysis** | Structured systems analysis — data flows, failure modes, leverage points, architecture (C4 + arc42). |
| **training-kit** | Build a self-paced training kit on any subject, for any audience, from what you can reach in your own environment. Fixes five settings first (subject, audience, where practice happens, the help beside the learner, what learners will be able to do) and settles every assumption on one page before writing, inventories the learners' real tasks and what the established trainings on the subject teach, and designs the path backward from the outcome, with one worked example running through it on practice files every learner has. Works for a tool learned in its own screens as well as for an assistant's chat. Ships a starter kit whose builder generates a small learning site from markdown, with progress, a workbook that keeps what the learner writes, a version and last-updated dates, and checks it; a published hands-on exercise as the form every unit is written in; a review checklist; and twelve briefs for reviewers who did not build the kit. |
| **value-analysis** | Structured value reasoning — value for whom, at what altitude, under what constraints. |
| **visual-usability** | Judge the rendered visual of a page or document — hierarchy, density, cognitive load, scannability, the 5-second first impression. Requires seeing the render. |

## Agents (`agents/`)

| Agent | What it does |
|-------|-------------|
| **apparatus-auditor** | Audit whether something has the operating apparatus it needs to actually work — what guarantees it gets written, what guarantees it gets read — or whether it is a prop that will die in a drawer. Reads your operating model as the yardstick, and grades against your real scale rather than a borrowed one. |
| **independent-discipline-reviewer** | Cold, fresh-eyes review of an artifact against one or more named discipline skills, run in its own context. It holds only independence — it loads the disciplines you name as review lenses, and writes a findings report rather than editing the artifact. |
| **prior-art-checker** | A deliberately blind evaluator. It receives only a functional description — never the artifact, its name, or what you think it matches — and names the established practice with the same function, with an honest account of what does not fit. "No match" is a valid, valuable answer. The blindness is the point: an evaluator told what you believe can only agree with you. |

## Reference packages (`packages/`)

| Package | What it is |
|---------|-----------|
| **observability-practice** | An observability Body of Knowledge (13 knowledge areas, 24 instruments, domain perspectives), plus a practice system, the SUD v2 instrument, a walk-before-run kit — a focused nine-page rendering for a team's first business process — and a one-page rendering of the model itself: its terms, how they connect, and where the methodology stops and implementation begins. |
| **observability-capability-gap.md** | A worked articulation of a platform capability gap against an observability standard — why dependency, producer, and internal errors fall outside a common APM metric model, and what that costs. |
| **splunk-apm-alert-coverage.html** | A one-page brief, opened in a browser, on which failures Splunk Observability Cloud APM can alert on and which it only records, walked step by step through one request and compared with AppDynamics. Each kind of step is checked against four questions (recorded, measured, alertable, names what broke); common statements about coverage are scoped to the steps they are true for; options to close the gaps and questions for the platform team follow. Sources are public product documentation. |
| **meeting-delegate** | A package for the meeting-delegate practice (start-here, the practice, acceptance test). |
| **portfolio-coverage-operating-perspective.md** | An operating perspective for reasoning about observability coverage across a service portfolio. |
| **ai-credit-cap-justification.md** | Argument architecture for justifying an AI-assistant credit-cap increase — the answer-with-context method, per-question structure, candidate framings, and cautions. |
| **design-for-operations.md** | A repeatable method for taking a business capability from architecture to observability — eight passes from surface discovery to signal placement and ownership, each producing an artefact and ending at a checkpoint. |
| **design-for-operations-operating-perspective.md** | The same method in activation form, written for an assistant that already holds the field rather than for a reader learning it — seven passes with the practice each activates, what each of the three views may not claim, the four concerns as competency questions, what code cannot yield, and where established practice runs out. A working draft under active development. |
| **assigning-business-work-to-levels.md** | A procedure for deciding whether a piece of business work is a capability, an intended flow, a stage, a process step, a component or an external dependency. Two tests decide it, a declared frame bounds it, and a worked example shows the shape. Written for an assistant reading whatever source material exists — source code, architecture documents, interview notes, a strategy deck — and built for a judgment that has several defensible answers rather than one: it takes a position on every assignment and records the frame that position depends on, whether it was read or inferred, and the reading it rejected, so a dissenter can see exactly what to argue with. States its own blind spots — parallel work, loops, exceptions, a changing unit of case. |
| **assessing-capability-observability.md** | The general form of the assessment: whether a business capability's behaviour can be determined from what its systems emit. States the claims it rests on — observability as a property of a traversal rather than of an inventory, the flow's boundary as the expectation's boundary, and the capability as the anchor because an expectation must outlive the implementation — then the method in four established steps, each carrying the published practice it descends from. Sets out the six levels, what each can report, and the four relations between them — which are not one ladder — along with the three distinctions that carry the most weight: two that mark a limit on what can be known, and one that marks only where measuring conventionally begins. Companion to `assigning-business-work-to-levels.md`: that one assigns a piece of work to a level, this one is the frame the levels sit in. |
| **what-each-level-can-report.md** | What observing each of the six levels can tell you. The level decides what a measure is counted on and the question decides its layer: business health and business impact are read at the flow, the stage and the step, each over its own scope, and components and external dependencies answer why. Names the established set of measures for each kind of part, treats an agent as its own system of interest with provisional measures, and gives the working rules for placing a measure and counting business impact in cases, wrong or late. Working rules, expected to change. Companion to `assessing-capability-observability.md`. |
| **design-for-operations-views-eshop.html** | A one-page example, opened in a browser, of design-time views of a business capability, drawn from the public source code of eShop, the open-source .NET reference store: online retail and the two capabilities inside it, two intended flows (placing an order, filling a basket), their stages and steps, the components that perform or support each step, and the external dependencies they rely on. Four views — the levels filled in, what each level reports, where a failure reaches, and an AI agent as a system of its own — each shown first on an invented home lender or on the general form with placeholder names, then on eShop, where the AI shopping assistant is drawn as one of the components; an overview with every stage opened closes the page. Companion to `what-each-level-can-report.md`. |
| **platform-capability-assessment-operating-perspective.md** | An operating perspective for the situation where a platform reports that a capability exists and the consuming team's need is still unmet — decomposing a capability claim into presence, coverage, and depth, naming the scope state it holds, and shaping a request that asks for published scope rather than a one-off exception. |
| **situation-to-form-operating-perspective.md** | An operating perspective for the whole path a rough request travels before it becomes something an organization holds — six decisions (capture the situation, name it against canon, record the route, set the weight, split the roles, become a real form), each with the established practice behind it. The frame of a two-part set; `practice-routing-operating-perspective.md` is its second link at working depth. |
| **practice-routing-operating-perspective.md** | An operating perspective for routing a problem stated in ordinary words to the established practice that addresses it — or refusing and naming the discipline that owns it. Covers the split between what is known about situations of a kind and what is true in one place, the index form with its does-not-answer veto, the fit test, and the two failure modes. |
| **copilot-training-kit** | Self-paced trainings on using GitHub Copilot in VS Code; no coding needed. Four trainings, each opening by saying what it needs from the ones before: Getting started (a first request, changing and undoing Copilot's work, having it explain code, custom instructions for a folder, and practice recipes), Skills, Custom agents, and Connecting your tools (connecting Copilot to GitHub). Every training makes its practice files by requests on the page, so nothing is downloaded. One help page and a glossary are shared by every training. Read it in a browser from `read-in-browser/README.html`, with progress and the learner's notes kept in the browser; `maintaining/` holds the guide, the page builder and its checks for extending it. |
| **copilot-overview-video** | A narrated overview, about two minutes long, of the trainings in `copilot-training-kit`: what each one is for and where to start. It comes in two versions with the same script: a page opened in a browser (captions, the transcript beside the player, a step for each scene, works with the sound off) and a video file with built-in captions plus a separate captions file. |
| **runbook-practice** | A practice for runbooks across a large estate of production alerts, split by reader. How alerts, dashboards, runbooks, escalation and postmortems fit together; the model of one runbook (its endings, when to escalate and when to declare an incident, its sections in reading order, and how to write one); what a responder records when closing an alert; a standard for scoring runbooks and setting a minimum for critical services; and a review loop for finding which alerts are noise and which runbooks are weak, fixing the worst first, and measuring the result. Incident coordination and alert design are out of scope and pointed to. Worked instances use public runbooks and public operations records. A draft, expected to change. |
| **bfo-stage-kit** | A kit an assistant follows over an application's code to describe one business flow (the case it carries, the states the case passes through and the stages they fall into) and then, for one stage, to write four files for the engineers who own the code: the stage drawn with its steps and the parts that carry them, what could be measured at each layer, the one alert that pages for the stage, and the runbook for whoever is paged. Every claim cites the code by file and line, and anything the code does not state is marked proposed with the reason. Written for GitHub Copilot Chat in agent mode with Python 3.9 or later; start with `USE.md`. Ships the blank register, the method's lists, the reference documents, the generator (Python standard library only) and a finished example on eShop, the open-source .NET reference store. `KNOWN-GAPS.md` says what a run is known to get wrong. |

## Install

Copy a skill folder into your environment's skills directory:

```
your-repo/.github/skills/<skill-name>/SKILL.md
```

Some skills include extra files — a `references/` subfolder, or a companion document. Copy the whole folder.

Agents go in the agents directory:

```
your-repo/.github/agents/<agent-name>.md
```
