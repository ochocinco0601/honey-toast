What Splunk APM alerts on, and what it only records

A draft from public product documentation, September 2026, written to be corrected by the team that runs the platform

When application performance monitoring (APM) moves from AppDynamics to Splunk Observability Cloud, the question comes up whether Splunk "covers" a service's dependencies. This page walks through one request and asks four things of each step: is a failure recorded, is it measured, can it raise an alert, and does the alert say what broke.

Splunk alerts where work enters a service, not on what the service calls

  • Splunk records every step of a request in the trace. It builds alertable metrics only where work enters a service (a request it receives, a message it consumes), plus calls to third-party HTTP APIs.
  • A failing database call, Kafka publish, call to another in-house service or internal step has no alert of its own.
  • If that failure brings the whole request down, the endpoint alert fires, but it does not name the database or topic. If the request survives, nothing alerts.
  • AppDynamics alerts on each database and remote service directly and by name. Switching loses that.
  • RED metrics generated for root spans of kind CLIENT, PRODUCER or INTERNAL cover work a service starts on its own, such as a scheduled job. They do not cover the calls made while handling a request, and alerts can use them only if they are monitoring metrics.

In one request, only the first step raises its own alert

A checkout service receives an order. While handling it, the service reads a database, calls a payment service, validates the cart and publishes an event to Kafka. The trace records each of these as a span. The first span of a trace is its root span; the others are steps inside it. Each span has a kind: SERVER for a request received, CLIENT for a call made, PRODUCER for a message sent, CONSUMER for a message received, INTERNAL for work inside the service. RED metrics are the standard three: requests, errors and duration.

Every step is recorded; database, Kafka and service calls lose their own alerts

"Is it covered?" gets a different answer depending on which of these is meant. Each one goes further than the one before it.

  1. Recorded: is the failure in the trace data at all?
  2. Measured: is it counted as metrics (requests, errors, duration) that can be charted?
  3. Alertable: can an alert fire on it without anyone looking?
  4. Names what broke: does the alert say which dependency or endpoint failed?

What each row rests on
Requests and consumed messages
Splunk creates its alertable metrics, called Monitoring MetricSets, "for spans where the span.kind has a value of SERVER or CONSUMER". Detectors, Splunk's alert rules, run on these; they are kept 13 months.
Third-party APIs
Only third-party or uninstrumented HTTP services that Splunk infers get Monitoring MetricSets. What the operation field holds for them is not documented.
Calls to in-house services
Error metrics come from SERVER and CONSUMER spans, so a call's error is counted at the service that received it, with all its callers mixed together. A call that fails before arriving (refused connection, DNS, timeout) has no SERVER span, so no metric counts it.
Database calls and Kafka publishes
Databases and topics get troubleshooting MetricSets only, which feed investigation views and are kept 8 days. AppDynamics health rules can target "all databases and remote services", and Kafka topics appear there as remote services.
Internal steps and self-started work
A failure the request survives stays in the trace. Splunk notes that self-initiated work has no SERVER or CONSUMER span. Where RED metrics are generated for root CLIENT, PRODUCER and INTERNAL spans, detectors can use them only if they are monitoring metrics.

Common statements about coverage are true for fewer steps than they sound

RED metrics are generated for root spans of kind CLIENT, PRODUCER or INTERNAL.

True for work a service starts on its own. Not true for the database calls, publishes, service calls and internal steps made while handling a request, because those are not root spans.

Outbound dependencies, messaging and internal processing are monitored.

True only when that work is the root of a trace. The gaps are in the dependency calls inside a request.

The data is in the traces.

True for question 1 on every row. It does not answer question 3: someone reads a trace after they already know to look.

Troubleshooting metrics already cover databases and topics.

True for question 2, for 8 days. Detectors run on monitoring metrics, not troubleshooting ones, so it does not answer question 3.

You can alert on trace attributes.

True for one to five attributes chosen in advance and added to endpoint and service metrics, within the licence limit. Not true for any attribute in the trace chosen after the fact.

A future analytics interface will cover it.

That describes searching traces for a pattern. It is not an alert that fires today.

Metrics measured by the calling service would close most gaps

For discussion. Which to use, and at what cost, is for the platform team and the application teams to decide.

  • Database calls: the service emits the OpenTelemetry metric db.client.operation.duration, which detectors can use like any custom metric. The standard is stable and reports per database, operation and table. Work falls on application teams.
  • Calls to in-house services: the service emits http.client.request.duration. That names the called service; naming the endpoint needs the opt-in url.template attribute. Application teams.
  • Kafka publishes: OpenTelemetry messaging metrics, whose standard is still in development. Application teams.
  • All of the above, plus internal steps: the platform derives metrics from every span kind in the OpenTelemetry Collector's span metrics connector. The component is alpha and needs cardinality limits. Platform team.
  • Self-started work: confirm that root-span metrics exist in the running environment, with a working alert on one such span. Platform team.

Five questions for the platform team would settle what is still unknown

  1. Are the RED metrics for root CLIENT, PRODUCER and INTERNAL spans monitoring MetricSets, which detectors can use, or troubleshooting ones?
  2. Do they apply to any span that is not the root of its trace?
  3. Do the services already emit http.client.request.duration or db.client.operation.duration? If they do, detectors can use them today.
  4. Can a custom MetricSet be defined on CLIENT spans for calls to in-house services? The documentation does not say.
  5. Which AppDynamics health rules on databases, remote services and error types are active today? That is what teams would actually lose.
