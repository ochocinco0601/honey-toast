# Proposed alerts for "Accept the order": M13 Orders past the acceptance promise, by state; M93 Orders cancelled in acceptance because payment failed

**Stage 2 of 4:** Accept the order, in flow Fulfilling a customer's order. Its steps: Step 2.1: The order is released for stock checking when the grace period ends; Step 2.2: Stock is confirmed for every item of the order; Other outcome: The order is cancelled because an item is out of stock; Expected outcome: Payment is taken for the order; Other outcome: The order is cancelled because payment failed; Other outcome: The order is cancelled at the customer's request. Each measure below is its own alert; whichever fires, follow its own entry in [RUNBOOK.md](RUNBOOK.md) (the runbook link below).

| | |
|---|---|
| **The question it answers** | **M13** How many orders have waited longer than the promise to be accepted, and in which state are they held?<br>**M93** How many orders entering acceptance are cancelled because payment failed? |
| **What it counts** | **M13** Orders past the acceptance promise, by state: SELECT "OrderStatus", count(*) FROM ordering.orders WHERE "OrderStatus" IN ('Submitted','AwaitingValidation','StockConfirmed') AND now() - "OrderDate" > interval '2 minutes' GROUP BY 1 (the interval is the stage's proposed promise); in the postgres container (az containerapp exec --name postgres --resource-group <rg>) run psql -U postgres -d orderingdb (counted on cases)<br>**M93** Orders cancelled in acceptance because payment failed: ordering-api log lines 'Handling integration event:' naming OrderPaymentFailedIntegrationEvent, one per order, searched over the window in the log store, against the orders that entered acceptance in it ("OrderDate" in ordering.orders) (counted on cases) |
| **Why it is proposed** | **M13** an order still in Submitted, AwaitingValidation or StockConfirmed past the promise has not been accepted when the shopper expects, and the moves out of AwaitingValidation and StockConfirmed strand it with nothing to move it again (lifecycle L04-L07, recovery stranded). This measure is not emitted yet; deployed as written, the alert fires on No data until it is.<br>**M93** a payment outage cancels every order that reaches StockConfirmed (L07), and none of them waits, so M13 stays flat while the shopper loses the order |
| **Cases stranded** | A case is stranded, with nothing in the application to move it on, when one of these moves does not happen: L04 Stock is confirmed for every item of the order, L05 The order is cancelled because an item is out of stock (The order stays in AwaitingValidation with nothing to move it: a failed publish is marked PublishedFailed and never sent again (Ordering.API/Application/IntegrationEvents/OrderingIntegrationEventService.cs:27-31; Catalog.API/IntegrationEvents/CatalogIntegrationEventService.cs:21-25; IntegrationEventLogEF/Services/IntegrationEventLogService.cs:19-23, 56-59); a consumer that throws still acknowledges the message, so it is gone (EventBusRabbitMQ/RabbitMQEventBus.cs:170-180); the poll re-sends only for Submitted (OrderProcessor/Services/GracePeriodOrdersRepository.cs:27). A message waiting in its queue for a stopped consumer moves on when the consumer returns); L06 Payment is taken for the order, L07 The order is cancelled because payment failed (The order stays in StockConfirmed with nothing to move it: Ordering API's publish failure is marked PublishedFailed and never retried (Ordering.API/Application/IntegrationEvents/OrderingIntegrationEventService.cs:27-31; IntegrationEventLogEF/Services/IntegrationEventLogService.cs:19-23, 56-59); Payment Processor's publish has no outbox and its failure throws out of the handler (PaymentProcessor/IntegrationEvents/EventHandling/OrderStatusChangedToStockConfirmedIntegrationEventHandler.cs:32), and every consumer acknowledges a message it failed on (EventBusRabbitMQ/RabbitMQEventBus.cs:170-180). A message waiting in its queue for a stopped consumer moves on when the consumer returns) |
| **Runbook link** | **M13** [its entry in RUNBOOK.md](RUNBOOK.md#alert-m13-orders-past-the-acceptance-promise-by-state)<br>**M93** [its entry in RUNBOOK.md](RUNBOOK.md#alert-m93-orders-cancelled-in-acceptance-because-payment-failed) |
| **Grouping** | **M13** By the state the case is in: `Submitted`, `AwaitingValidation`, `StockConfirmed`. Its runbook entry groups the cases by state and works each state's tests.<br>**M93** By the move the case left by: L07 from `StockConfirmed`. Its runbook entry works that state's tests. |
| **Threshold** | *Operator value, not set here.* For each measure, the value at which the alert fires. Whether it pages a person, opens a ticket or shows on a dashboard is the operators' decision. |
| **No data** | Each alert also fires when its measure cannot be counted: the query or search itself fails for longer than the window. A count of events that finds none in a window is zero, not missing data. A count fails when what it is read from is down, and then cases go wrong unseen. What it counts says where each is read. |
| **Age bound** | *Operator value.* For M13, the stage's promise: proposed: 2 minutes from entering Submitted, read from the timing of L03, L04 and L06: a 1-minute grace period and up to 30 seconds to the next poll (OrderProcessor/appsettings.json:15-16; OrderProcessor/Services/GracePeriodManagerService.cs:17, 51), then 10 seconds before StockConfirmed and 10 before Paid (Ordering.API/Application/Commands/SetStockConfirmedOrderStatusCommandHandler.cs:22; Ordering.API/Application/Commands/SetPaidOrderStatusCommandHandler.cs:22). The stage is entered when the record is created, so a case's age in it is now minus "OrderDate" (Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:58) |
| **Window** | *Operator value, not set here.* How long the condition must hold before the alert fires. What the design assumes about time: L03: Grace period GracePeriodTime 1 minute, polled every CheckUpdateTime 30 seconds (OrderProcessor/appsettings.json:15-16; OrderProcessor/Services/GracePeriodManagerService.cs:17, 34, 50-52). Every run re-publishes for each order still Submitted (OrderProcessor/Services/GracePeriodManagerService.cs:54-61). The bus's retry policy (RetryCount 10, EventBusRabbitMQ/EventBusOptions.cs:6) never retries a failed publish: Execute is given an async lambda, so the failure lands in the returned task, not the call (EventBusRabbitMQ/RabbitMQEventBus.cs:57, 302-314; Polly's Execute overloads, https://www.pollydocs.org/api/Polly.ResiliencePipeline.html); L04: 10 seconds of simulated work before the status is set (Ordering.API/Application/Commands/SetStockConfirmedOrderStatusCommandHandler.cs:21-22). Ordering API consumes its queue with one consumer on one channel (EventBusRabbitMQ/RabbitMQEventBus.cs:246, 270-277), so these waits queue behind one another; L05: 10 seconds of simulated work before the status is set (Ordering.API/Application/Commands/SetStockRejectedOrderStatusCommandHandler.cs:21-22), queued behind the other waits as in L04; L06: 10 seconds of simulated work before the status is set (Ordering.API/Application/Commands/SetPaidOrderStatusCommandHandler.cs:21-22), on the same single consumer as L04; L07: No wait and no timeout: unlike L06, Ordering API sets Cancelled at once (Ordering.API/Application/Commands/CancelOrderCommandHandler.cs:19-29), but on the same single consumer as L04, so it queues behind the 10-second waits there (EventBusRabbitMQ/RabbitMQEventBus.cs:246, 270-277). No clock watches a message waiting in its queue, and the queue sets no expiry (EventBusRabbitMQ/RabbitMQEventBus.cs:258-263); L08, L09, L10: No timeout of its own: the mobile app's HttpClient has no handler, so it keeps .NET's default timeout of 100 seconds and makes one attempt (ClientApp/Services/RequestProvider/RequestProvider.cs:12-18; default: https://learn.microsoft.com/dotnet/api/system.net.http.httpclient.timeout); Mobile BFF's route and Ordering API's cancel endpoint set none (eShop.AppHost/Extensions.cs:144-146; Ordering.API/Apis/OrdersApi.cs:22-49), and the cancel itself waits for nothing (Ordering.API/Application/Commands/CancelOrderCommandHandler.cs:19-29) |
| **Symptom, not cause** | It fires on what happens to cases, not on any component's errors. Telling causes apart is the runbook's job. |
| **Exists today** | M13: no, proposed; M93: yes, Ordering.API/Application/IntegrationEvents/EventHandling/OrderPaymentFailedIntegrationEventHandler.cs:10 (the line is written once per delivered event; the cancellation it leads to writes the same status and description as a shopper's own, Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:142-153, so the order record alone cannot tell them apart) |
